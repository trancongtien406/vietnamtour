# UI Illustration

## Purpose

UI illustration exists to improve comprehension, feedback, onboarding, identity,
or emotional tone. It is not filler.

## Good use cases

- high-value empty state;
- onboarding concept;
- success/reward state;
- feature education;
- emotional checkpoint;
- branded consumer surface.

## Weak use cases

- repeated table empty states;
- dense admin widgets;
- every settings section;
- every action card;
- situations where an icon is enough.

## Required spec fields

- role;
- purpose;
- display context;
- real rendered size;
- visual weight relative to copy/CTA;
- background mode;
- style source;
- safe area;
- state variants;
- constraints.

## Composition rule

Design for the final container, not for an imaginary artboard.

The illustration must not steal the action hierarchy unless it is itself the
content.

Prefer live interface text over baked text inside raster artwork.

## Production separation

When the interface is coded, generate the illustration separately from cards, titles, buttons, prices, dynamic labels, and provider metadata.

The code owns layout and text. The asset owns the illustration.
